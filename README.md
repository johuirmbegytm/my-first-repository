Дізнаюся, що переноси рядків у текстових файлах кодуються по-різному в різних операційних системах (Windows, Linux, macOS), і це може спричиняти проблеми при спільній роботі в Git. Щоб уникнути плутанини, Git дозволяє уніфікувати переноси рядків через налаштування core.autocrlf і core.safecrlf.

Налаштовую ці параметри через термінал, в моєму випадку для Windows, використовуючи команди:

```bash
git config --global core.autocrlf true
git config --global core.safecrlf warn
```

![8](https://github.com/johuirmbegytm/my-first-repository/blob/main/images/8.png)

Дізнаюся, що стандартну назву гілки в Git змінили з master на main, щоб зробити термінологію більш інклюзивною. Встановлюю звичайну гілку main за допомогою команди:

```bash
git config --global init.defaultBranch main
```

Дізнався, що кожен термінал має свою поточну директорію, яку можна перевірити командою pwd, а змінити — через cd. Це важливо перед ініціалізацією Git-репозиторію.

Дізнався, як навігувати терміналом за допомогою команд cd, pwd, відносних і абсолютних шляхів, а також як використовувати автозаповнення через Tab. І найголовніше — ти ініціалізував Git-репозиторій у кореневій директорії проєкту за допомогою:

```bash
git init.
```

Дізнався, як створити файл hello.html з текстом "Hello, World!" через термінал, перевірити поточну директорію (pwd), перейти до потрібної (cd), і відкрити файл у VS Code (code). Це перший крок до роботи з Git і веброзробки.

![12](https://github.com/johuirmbegytm/my-first-repository/blob/main/images/12.png)

Дізнався, що Git не відстежує файли автоматично — їх потрібно вручну додати до staging area командою ```git add```, після чого створити коміт за допомогою ```git commit -m "Initial commit"```. Коміт — це знімок змін у репозиторії, і до нього варто додавати лише ті файли, які справді мають бути збережені. Ти також дізнався, що повідомлення до коміту потрібно писати в лапках, і що staging area ще називають індексом. Крім того, ти навчився створювати файли через термінал (```echo "Hello, World!" > hello.html```), відкривати їх у VS Code (code hello.html), перевіряти поточну директорію (pwd) і переходити між папками (cd). Ти зрозумів різницю між абсолютними та відносними шляхами, як працюють спеціальні символи . і .., і як Tab допомагає автозаповнювати назви файлів. Нарешті, ти ініціалізував репозиторій (```git init```) і зробив перший коміт, що означає — твій проєкт тепер під контролем версій.

![13](https://github.com/johuirmbegytm/my-first-repository/blob/main/images/13.png)

![14](https://github.com/johuirmbegytm/my-first-repository/blob/main/images/14.png)

Дізнався, що команда ```git status``` показує поточний стан репозиторію — на якій гілці ти працюєш, чи є незбережені зміни, і чи є щось для коміту. Якщо бачиш "working tree clean", це означає, що всі зміни вже закомічені, і репозиторій у чистому стані. Це корисна команда для контролю перед кожним комітом, щоб не пропустити важливі файли або випадково не закомітити зайве.

![15](https://github.com/johuirmbegytm/my-first-repository/blob/main/images/15.png)

Дізнався, що команда ```git status``` показує, чи були змінені файли з моменту останнього коміту, і чи додані вони до staging area. Після того як кіт випадково змінив hello.html, я побачив, що файл модифікований, але зміни ще не додані до коміту. Потім ти використав git diff, щоб побачити точну різницю між поточним вмістом файлу та останньою збереженою версією в репозиторії. Ця команда показала, що рядок "Hello, World!" був замінений на "Hello, Meow! World! Meow! Meow! Meow!". Ти також дізнався, як читати формат виводу ```git diff```, де - означає видалені рядки, а + — додані. Це дозволяє легко знаходити небажані зміни та вирішувати, що з ними робити.

![16](https://github.com/johuirmbegytm/my-first-repository/blob/main/images/16.png)

Дізнався, що командою git restore . можна повернути всі файли в поточній директорії до останнього закоміченого стану, ефективно скасувавши всі незбережені зміни. Це особливо корисно, коли трапляються випадкові правки, як от "котячий саботаж". Також я дізнався, що можна відновлювати окремі файли (```git restore hello.html```) або цілі директорії. Після відновлення я перевірив стан репозиторію через git status і переконався, що робоча директорія знову чиста. Крім того, я засвоїв, що стара команда git checkout для скасування змін була замінена на більш зрозумілу git restore, яка зменшує ризик помилок.

![17](https://github.com/johuirmbegytm/my-first-repository/blob/main/images/17.png)

Дізнався, як скасувати помилкові зміни, навіть якщо вони вже були додані до staging area. Спочатку я випадково обгорнув текст у тег ```<head>``` замість ```<h1>```, і ці зміни були проіндексовані. Щоб їх прибрати зі staging area, я використав команду ```git restore --staged```., яка повернула файл до статусу "змінений, але не готовий до коміту". Потім, щоб повністю відкинути зміни у файлі, я застосував ```git restore``` ., і робоча директорія стала чистою. Я також дізнався, що ```git restore``` має два режими: ```--staged``` для індексу і ```--worktree``` для робочої директорії, і їх можна комбінувати для повного відновлення стану файлів.

![18](https://github.com/johuirmbegytm/my-first-repository/blob/main/images/18.png)

Дізнався, як виправити останній коміт у Git за допомогою команди git commit --amend. Спочатку я додав до файлу hello.html тег ```<h1>```, закомітив зміни, але помилився в повідомленні коміту. Я замінив його на правильне — "Added HTML tags to hello.html" — використовуючи --amend. Потім я додав ще HTML-структуру з тегами ```<html>``` і ```<body>```, проіндексував зміни (```git add hello.html```) і знову використав ```git commit --amend```, щоб оновити останній коміт і включити всі правки в один запис. Це дозволяє зберігати історію змін чистою та зрозумілою, особливо коли потрібно пояснити, хто і навіщо вніс певні зміни.

Дізнався, що команда ```git log``` показує історію комітів у репозиторії, включаючи унікальний SHA-1 хеш, автора, дату та повідомлення коміту. Цей хеш можна використовувати як посилання на конкретний коміт у командах типу ```git diff, git show або git revert```. Крім повного хешу, Git дозволяє посилатися на коміти через скорочений хеш, теги, назви гілок, спеціальне посилання HEAD, а також відносні посилання типу HEAD~2 або HEAD^. Це дає гнучкість у навігації по історії змін і дозволяє точно вказувати, з якою версією коду ти хочеш працювати.


![19](https://github.com/johuirmbegytm/my-first-repository/blob/main/images/19.png)

Дізнався, що теги в Git — це зручні мітки для важливих комітів, які дозволяють легко повертатися до певної версії коду. Вони особливо корисні для публічних релізів, як-от версія 1.0, яку я щойно створив командою git tag 1.0. Тепер інші проєкти можуть посилатися саме на цю стабільну версію, навіть якщо ти пізніше внесеш зміни. Також навчився переглядати всі теги в репозиторії через команду git tag. Це основа для керування версіями, і вона допомагає уникати проблем із сумісністю, як у прикладі з оновленням бібліотеки.

![20](https://github.com/johuirmbegytm/my-first-repository/blob/main/images/20.png)

Дізнався, що гілки в Git дозволяють працювати над новими функціями або виправленнями ізольовано від основного коду, не порушуючи стабільну версію проєкту. Команда git branch показує всі гілки, і за замовчуванням у новому репозиторії є лише одна — main. Гілка — це просто вказівник на останній коміт, а HEAD — це вказівник на активну гілку. Коли ти перемикаєшся між гілками, HEAD змінює своє положення відповідно.

Також дізнався про різні стратегії роботи з гілками: централізовану (всі працюють на main), з окремими гілками для кожної функції (Feature Branch Workflow), складну структуру з гілками для розробки, релізів і гарячих виправлень (Gitflow), а також форки, які часто використовуються в open-source. Кожна стратегія має свої переваги залежно від розміру команди, складності проєкту та циклу релізів.

![21](https://github.com/johuirmbegytm/my-first-repository/blob/main/images/21.png)

Дізнався, як створювати нові гілки в Git (```git switch -c style```) для ізольованої розробки функцій, щоб не порушувати стабільний код у main. У гілці style я створив файл style.css, додав стилі для заголовка, оновив hello.html, проіндексував і закомітив зміни. Потім я переключився назад на main (```git switch main```) і побачив, що стилі не з’явились — бо вони існують лише в гілці style. Це показує, як гілки дозволяють працювати над окремими фічами незалежно. Після цього я повернувся в style (```git switch style```) і переконався, що всі зміни збережені там. Таким чином, я освоїв базову роботу з гілками: створення, перемикання, ізоляція змін і підготовка до злиття.

![22](https://github.com/johuirmbegytm/my-first-repository/blob/main/images/22.png)

Дізнався, як об'єднувати гілки в Git, щоб перенести зміни з фічевої гілки (style) до основної (main). Спочатку я переключився на main (```git switch main```), потім виконав злиття (```git merge style```), і переконався, що файл style.css з'явився в директорії — отже, злиття пройшло успішно. Я також перевірив історію комітів (```git log```), щоб упевнитися, що коміти з style тепер є частиною main. Після цього я видалив гілку style (```git branch -d style```), щоб підтримувати порядок у репозиторії. І нарешті, я дізнався, що при злитті можуть виникати конфлікти, якщо однакові частини файлу змінені в різних гілках — такі ситуації потребують ручного вирішення.

![23](https://github.com/johuirmbegytm/my-first-repository/blob/main/images/23.png)

![24](https://github.com/johuirmbegytm/my-first-repository/blob/main/images/24.png)

![25](https://github.com/johuirmbegytm/my-first-repository/blob/main/images/25.png)

Я навчився ефективно переглядати історію комітів у Git за допомогою ```git log```. Спочатку я побачив стандартний багаторядковий формат, який містить хеш коміту, автора, дату та повідомлення. Потім ти спробував ```git log --oneline```, що стискає кожен коміт до одного рядка — зручніше для швидкого перегляду. Далі ти експериментував з фільтрами: ```--max-count, --since, --until, --author, --all```, щоб вибірково переглядати історію.
Найцікавіше — я використав ```git log --format="%h %ad | %s%d [%an]" --date=short```, щоб налаштувати вивід: короткий хеш, дата, повідомлення, декорації (наприклад, HEAD або тег), і автор. Це дало тобі компактний, інформативний вигляд історії. І нарешті, я зберіг цей формат як дефолтний для поточного репозиторію через git config, щоб не вводити його щоразу.
Це дає контроль над тим, як ти переглядаєш історію змін, що особливо корисно, коли проєкт розростається і потрібно швидко знаходити потрібні коміти.

![26](https://github.com/johuirmbegytm/my-first-repository/blob/main/images/26.png)

Я навчився порівнювати зміни між комітами за допомогою ```git diff```. Спочатку я переглянув історію окремих файлів (```git log hello.html і git log style.css```), щоб побачити, які коміти їх змінювали. Потім я використав ```git diff 1.0 HEAD```, щоб порівняти стан файлів між тегом 1.0 і останнім комітом. У результаті я побачив, що до hello.html було додано з посиланням на style.css, а сам файл style.css був створений з CSS-правилом для червоного заголовка.
Я також засвоїв, що порядок у ```git diff``` має значення: Git показує, як змінювався код від першого коміту до другого. Це дозволяє точно відстежувати, які правки були внесені, і хто їх зробив. Такі порівняння — ключовий інструмент для рев'ю коду, пошуку помилок і розуміння еволюції проєкту.
Я створив гілку experiment, зробив кілька комітів, а потім вирішив, що експеримент не вдався. Командою ```git reset main``` я повернув гілку до стану main, але зміни залишились у робочій директорії. Це називається ```soft reset``` — коміти скасовані, але файли залишились. Потім ти виконав ```git restore``` ., щоб прибрати ці зміни з робочої директорії. Це очистило hello.html, але experiment.html залишився, бо він був untracked — Git його не контролює. Я видалив його вручну через rm experiment.html. Після цього git status показав, що все чисто. Я також дізнався, що ```git reset --hard``` міг би зробити все це одразу: скасувати коміти, прибрати зміни і очистити staging area. Але така команда небезпечна — вона безповоротно стирає все, тому її треба використовувати обережно. Нарешті, я зрозумів різницю між ```git reset і git restore```: перша змінює положення гілки, друга — лише файли в робочій директорії.

Створюю новий репозиторій

![29](https://github.com/johuirmbegytm/my-first-repository/blob/main/images/29.png)

Я вже мав локальний репозиторій зі своїм кодом, і настав час підключити його до GitHub, щоб синхронізувати зміни та зручно ділитися проєктом. Я обрав підхід для нових проєктів: спочатку створив репозиторій локально за допомогою ```git init```, а тепер додав віддалений репозиторій.

Я виконав команду:
```bash
git remote add origin https://github.com/johuirmbegytm/my-first-repository.git
```
Цим я додав GitHub-репозиторій як віддалений з іменем origin. Щоб переконатися, що все працює правильно, я запустив:
```git remote -v``` 
І побачив очікуваний результат:
```
origin https://github.com/johuirmbegytm/my-first-repository.git (fetch) origin https://github.com/johuirmbegytm/my-first-repository.git (push)
```

Це підтвердило, що мій локальний репозиторій успішно підключений до GitHub. Тепер я готовий пушити свої зміни та працювати з репозиторієм у хмарі.

![30](https://github.com/johuirmbegytm/my-first-repository/blob/main/images/30.png)

Я щойно завершив важливий етап у роботі з Git: підключив свій локальний репозиторій до GitHub і синхронізував зміни.

```git push origin main``` 

Це дозволило мені відправити всі локальні коміти на GitHub. Після автентифікації (ввівши логін і токен), Git успішно передав мої файли. У терміналі я побачив підтвердження 
Потім я перевірив, чи є нові зміни на GitHub, і виконав:

```git pull origin main``` 

Це підтягнуло останні оновлення з віддаленого репозиторію до мого локального. Тепер мій проєкт повністю синхронізований.
Я засвоїв базовий цикл роботи з GitHub:
1.	pull — отримати останні зміни
2.	edit — внести свої правки
3.	commit — зафіксувати зміни
4.	push — відправити їх на GitHub

Я розібрався з тим, як працює переписування історії комітів у Git — і чому це може бути небезпечно при роботі з публічними репозиторіями.
Ось ключові висновки:
•	Переписування історії через ```git amend```, ```git reset``` або ```git revert``` змінює структуру комітів. Це допустимо для локальних гілок, але ризиковано для публічних репозиторіїв.
•	Якщо я зміню коміти після того, як вже запушив їх на GitHub, мої колеги можуть зіткнутися з помилками при спробі запушити свої зміни — бо їхня історія вже не збігається з оновленою.
•	Золоте правило: ніколи не переписуй публічну історію. Якщо потрібно щось виправити — краще зробити ```git revert```, який створює новий коміт, що скасовує попередній.
•	Якщо все ж потрібно переписати історію (наприклад, щоб прибрати конфіденційні дані), треба попередити всіх учасників, щоб вони синхронізували свої гілки.
•	```git push --force``` — це потужна, але небезпечна команда. Вона може стерти чужі зміни. Якщо вже доводиться її використовувати, краще застосовувати ```git push --force-with-lease```, яка попереджає про можливі конфлікти.
Це знання допоможе мені уникати помилок у командній роботі та краще контролювати історію змін.
